# Layer2-5 共享卷积块 Pipeline II=1 系统实现说明

## 1. 文档目标与结论

本文面向 `layer2-5` 共享 `ConvIco(r=1)` 硬件实现，系统总结“如何将关键流水环的 `II` 压到 `1`”所做的全部关键改动。文档同时服务两类场景：

1. 课堂/答辩汇报：强调为什么要改、改了什么、效果是什么。
2. 论文“系统实现”章节：强调架构分层、工程实现细节与可验证证据链。

核心结论是：

1. 本项目不是通过单一 pragma 达到 `II=1`，而是通过“架构分层 + 数据通路重构 + 定点量化 + HLS 约束协同”实现。
2. `II=1` 的达成主要体现在关键循环级 pipeline（尤其 `pad_ico_quantized` 与主计算空间循环），而非顶层函数总 interval。
3. 该结果建立在完整演进路径上：`3.22` 结构重构打通主路径，`3.24` 定点量化提供成本与时序空间，`3.24 A/B/C/D` 将分层骨架落地并满足全部 loop 约束。

---

## 2. 问题起点：为什么原始实现难以达到 II=1

根据策略跟踪文档，早期实现存在三类结构性瓶颈（对应“当前瓶颈位置标注图”）：

1. 输入侧瓶颈（B1）：
`PadIco` 阶段出现多条 `input_r_load_* due to limited memory ports`，并有 `pad_ico_Pipeline_VITIS_LOOP_76_2`、`Final II = 27` 的历史现象。  
本质问题是输入访存并行度不足，流水启动间隔被端口冲突抬高。  
直白地说：这一段每次迭代要同时读很多输入点，但底层存储端口数不够，读请求会排队。排队后，pipeline 不能每拍都发新迭代，只能“等上一批读完再发下一批”，所以 `II` 被顶到 `27`，也就是平均要隔 `27` 个周期才能启动下一次迭代。

2. 累加侧瓶颈（B2）：
主计算从单点串行 `sum += ...` 出发，局部累加链依赖重，HLS 难以持续发射新迭代。  
本质问题是 loop-carried dependence 过强。
直白地说：前一次加法结果还没写稳，后一次加法就必须等它，导致“下一拍想算也算不了”。这种前后强依赖会把流水线变成“走一步等一步”，很难做到每拍发射。

3. 输出侧瓶颈（B3）：
后处理与写回边界不清晰，容易与主计算阶段争用数据通路。  
本质问题是输出收尾阶段没有模块化，难以调度重叠。
直白地说：输出这部分像“清理现场”和“搬运结果”混在一起做，主计算也在抢同一条路，最后谁都跑不顺，流水线就容易出现停顿。

因此，本项目的优化目标不是“继续调频”或“泛化加 pragma”，而是将上述三类瓶颈分别映射到架构模块并逐项改造。

## 3. 总体架构：按“5 层模型”组织优化目标

本实现对齐 `layer2-5论文插图增强版架构图-中文.md`，采用五层架构：

1. 配置与调度层（S0）：
`层选择器`、`帧与 Tile 调度器`、`地址与 Bank 控制器`、`OC 与 RO 分发控制器`。

2. 输入准备层（S1）：
`输入帧缓冲` -> `几何预处理引擎` -> `PadIco 与重排映射器` -> `填充帧 SRAM` -> `空间窗口与输入 Tile 暂存`。

3. 参数准备层（S2）：
`紧凑权重 SRAM` + `Kernel 展开索引 SRAM` -> `索引译码` -> `展开后的 3x3 Kernel 缓存`。

4. 共享计算与累加层（S3）：
`共享 ConvIco 窗口 MAC 引擎` + `IC/OC 分块控制器` + `局部输出 Tile 累加器` + `输出 Tile SRAM`。

5. 输出收尾层（S4）：
`输出 Tile 极点清理` -> `局部极点平滑` -> `写回缓冲` -> `输出全局存储`。

这五层对应一个关键思想：  
把“一个大函数里混杂的几何处理、卷积、后处理”拆成可调度的结构单元，再针对每层做并行化与依赖削减，最终让关键循环具备 `II=1` 的条件。
直白地说：先把“大杂烩流程”拆成“分工明确的流水工位”，每个工位单独优化，再串起来，系统才有机会稳定做到每拍推进。

## 4. 关键改动全景：为什么要改、改了什么、效果是什么

### 4.1 阶段一（2026-03-22）：先打通主路径结构

### 改动 A：单点串行累加 -> 局部 `output_tile` 累加

- 为什么要改：
单点 `sum += ...` 形成长依赖链，是主计算吞吐瓶颈。
- 改了什么：
按 `co/ro` 组织局部 tile，先在 tile 内累加，再统一处理。
直白地说：不再“算一个点就立刻改一次总输出”，而是先把一小块结果放到本地缓冲里集中累加，等这一小块算完整再统一处理。
- 效果是什么：
显著降低主路径串行性，`Total Latency` 从 `6213631061` 降到 `498988881 cycles`（约 `-91.97%`）。

### 改动 B：权重按需展开 -> 局部 kernel 缓存

- 为什么要改：
每个空间点重复索引展开会拖慢 MAC 数据供给。
- 改了什么：
将 `kernel_expansion_idx` 驱动的展开结果提升为局部 `3x3` kernel 缓存。
直白地说：先把“权重索引翻译”这件事在局部做完并缓存起来，后面的 MAC 直接拿现成小块权重，不用每次重复查表和展开。
- 效果是什么：
减少重复索引解析，参数路径更稳定，MAC 环更容易 pipeline。

### 改动 C：顶层输出后处理 -> 局部 tile 后处理

- 为什么要改：
顶层 `output` 直接回改易引发读写竞争。
- 改了什么：
极点清理与平滑迁移到局部 tile，再统一写回。
直白地说：先在本地把“脏活细活”做完，再一次性写回总输出，避免边计算边改全局结果。
- 效果是什么：
输出路径与主计算初步解耦，后续阶段化改造成为可能。

### 改动 D：关键数组结构化分区

- 为什么要改：
不增加存储并行端口，`II=1` 只会停留在目标值而非达成值。
- 改了什么：
对 `padded_frame` 与 `weight` 关键维度执行 `ARRAY_PARTITION`。
直白地说：把关键数组按访问维度拆成多个 bank，相当于把单车道改成多车道，让并行读取真的跑起来。
- 效果是什么：
窗口读取与权重访问并行度提高，为后续 `II=1` 奠定物理端口基础。

---

### 4.2 阶段二（2026-03-24）：定点量化为流水和资源“腾空间”

### 改动 E：建立可配置定点类型边界

- 为什么要改：
结构重构后仍需控制资源与时序成本，避免“可跑但代价过高”。
- 改了什么：
在 `ico_conv_layer2_5.hpp` 中引入可配置位宽，收敛到：
`input_t=16,4`、`weight_t=14,3`、`act_t=24,8`、`acc_t=40,18`。
直白地说：给不同数据路径配不同“位宽档位”，输入和权重尽量紧凑省资源，内部累加留足位宽避免误差失控。
- 效果是什么：
相较 `3.22` 稳定版，`Total Latency` 进一步降到 `315787473 cycles`，`BRAM`、`DSP` 明显下降。

### 改动 F：保持 Host 接口 float，内部路径定点化

- 为什么要改：
需要兼顾现有 Python/C 验证链路与硬件实现优化。
- 改了什么：
接口仍用 `data_t=float`，核心计算路径在函数内部转 `input_t/weight_t/act_t/acc_t`。
直白地说：对外继续说“float 语言”（方便沿用现有测试数据），对内改成“定点语言”（让硬件更快更省）。
- 效果是什么：
验证流程不破坏，硬件路径可控收敛，为后续结构深化提供稳定基础。

---

### 4.3 阶段三（2026-03-24 A/B/C/D）：对齐最终架构图的骨架落地

### A：输入侧 staging 重构（S1）

- 为什么要改：
历史 `PadIco` 端口冲突说明输入层仍是 pipeline 入口瓶颈。
- 改了什么：
新增 `stage_input_frame_quantized()`，形成 `staged_input -> pad_ico_quantized -> padded_frame` 链路；并对 `staged_input/padded_frame` 空间维做 complete partition。
直白地说：在 `PadIco` 前加了一个“输入中转站”，先把数据整理好再送去几何预处理，同时把关键缓存拆并行端口，减少读口打架。
- 效果是什么：
输入准备层从“顶层大数组直接访问”转为“局部缓冲驱动”，关键 `pad_ico_quantized` 循环具备 `II=1` 条件。

### B：局部部分和组织重构（S3）

- 为什么要改：
`output_tile` 的读改写依赖仍会限制发射间隔。
- 改了什么：
引入 `OC_TILE=2`、`co_base` 调度与 `ri_partial[OC_TILE][RIN][...]`，先按 `ri` 计算 partial sum，再做 `ci` 级归并写回 `output_tile`。
直白地说：把“大账本”拆成“小账本 + 总账本”，先做 `ri` 小计，再做 `ci` 汇总，避免所有累加都挤在同一个热点位置。
- 效果是什么：
把“边算边全局累加”改成“分段累加后归并”，依赖链缩短、调度更规则。

### C：输出路径阶段化（S4）

- 为什么要改：
后处理与写回混在一起会引入额外调度耦合。
- 改了什么：
显式拆分 `post_process_output_tiles()` 和 `writeback_output_tiles()`，并设置 `output_post` 作为阶段边界。
直白地说：把输出流程拆成“本地加工”和“最终出货”两段，中间用 `output_post` 作为交接缓冲，职责更清楚。
- 效果是什么：
输出收尾链路结构清晰，便于独立 pipeline 与后续 dataflow 扩展。

### D：顶层流程收束（S0 贯穿 S1~S4）

- 为什么要改：
需要将零散优化组织成可复用的共享参数化主干。
- 改了什么：
顶层形成固定流程：
`stage_input -> pad_ico_quantized -> init_output_tiles -> main_conv/partial_sum -> post_process -> writeback`。
直白地说：把整段计算固化成一条可复用的装配线，数据按固定站点流动，不再是零散函数临时拼接。
- 效果是什么：
调度层可统一控制，结构语义与论文架构图一致，便于复现与扩展。

## 5. HLS 级实现细节：II=1 不是口号，而是约束协同结果

### 5.1 Pipeline 约束：关键循环显式 `II=1`

当前实现在以下关键路径显式使用 `#pragma HLS PIPELINE II=1`：

1. 输入量化 staging 循环（输入准备层）。
2. `pad_ico_quantized` 主空间循环（几何预处理层）。
3. 输出 tile 初始化与写回循环（输出路径）。
4. 主计算空间循环（`sp` 维）与 `ci` 归并循环（共享计算层）。

该设计将“希望 II=1”转化为“每层关键循环都声明 II=1 目标”。

### 5.2 存储并行化：`ARRAY_PARTITION` 直击端口瓶颈

主要策略：

1. `staged_input`、`padded_frame` 在空间维 complete partition。
2. `output_tile`、`output_post` 在 `OC/RO/H/W` 关键维分区。
3. `ri_partial` 在 `OC/RIN/H/W` 关键维分区。
4. `weight` 的输出通道维做 cyclic 分区，邻域维 complete 分区。

作用机制是：  
把“一个端口服务多次访问”的冲突，变成“多 bank 并行访问”，从根源改善 pipeline 发射能力。
直白地说：原来是很多人抢一个窗口读数据，现在改成分多个窗口并行读，自然就不容易堵车。

### 5.3 计算并行化：`UNROLL` + 局部缓存配合

1. `kernel_tile` 与 `3x3` 邻域循环 complete unroll。
2. `coo` 维并行展开（`OC_TILE=2`）。
3. `load_expanded_kernel()` 内联并局部缓存展开权重。

这让每个 pipeline 周期内可完成更多固定模式运算，减少控制分支扰动。

### 5.4 依赖链缩短：分层累加代替单链累加

由“单点串行累加”重构为：

1. `conv` 先写入 `ri_partial`
2. `ri_partial` 再按 `ri` 归并为 `ci_sum`
3. `ci_sum` 最后写回 `output_tile`

这种分层累加直接削弱 loop-carried dependence，是 II 压降的核心结构原因。
直白地说：先把小账分开记，再集中结算，不再所有人盯着同一本账本改来改去，等待链条就会明显缩短。

## 6. 关键证据：从历史阻碍到当前状态

### 6.1 历史阻碍（论文原因点）

策略跟踪文档记录的关键现象：

1. `input_r_load_* due to limited memory ports`
2. `pad_ico_Pipeline_VITIS_LOOP_76_2`
3. `Final II = 27`

这些现象定义了“为什么必须做输入侧重构与存储分区”。
其工程含义可概括为：  
`PadIco` 的读访问需求量大于当时存储可同时提供的读口能力，导致读冲突反复发生，最终表现为 loop 吞吐下降（`II` 从理想值 `1` 被抬高到 `27`）。

### 6.2 当前状态（2026-03-24 15:47:58 快照）

根据 `layer2-5_details/2026-03-24_154758_csynth_key.md`：

1. `pad_ico_quantized` 关键 pipeline 记录为 `Final II = 1`
2. `All loop constraints were satisfied`
3. `Estimated Clock = 4.209ns`，`Total Latency = 261686621`

说明当前版本已在关键循环层面实现 `II=1`，并完成从“历史瓶颈暴露”到“结构化解耦与调度达成”的闭环。

## 7. 总体技术贡献（可直接用于论文小结）

1. 提出并实现了面向 `layer2-5` 共享卷积块的分层硬件架构，将输入几何处理、参数准备、共享计算、输出收尾解耦为可调度模块。
2. 通过 `staging + partition + partial-sum` 三联策略，系统性降低 loop 依赖与端口冲突，推动关键流水环 `II` 收敛至 `1`。
3. 构建了“结构重构 -> 定点收敛 -> 骨架落地 -> loop 约束满足”的可复现实验路径，而非一次性调参结果。
4. 在保证 Python/C 验证链路可延续的前提下完成内部定点化，实现工程可验证性与硬件优化目标的统一。

## 8. 当前边界与后续工作

虽然关键循环已达到 `II=1`，但工程上仍有后续空间：

1. A/B/C/D 版本资源代价较高（尤其 `BRAM/LUT`），需继续做“资源回收版”。
直白地说：这版已经跑得更顺了，但“仓库和逻辑门”用得偏多，能跑不代表最省资源，还要继续瘦身。
2. 输入侧可继续推进更细粒度分块与 bank 复用，降低缓冲膨胀。
直白地说：输入缓存现在有点“开太大”，后面要把切分做细、复用做强，减少不必要的存储占用。
3. 在保持当前 loop 约束满足的前提下，评估双缓冲与顶层 `dataflow` 的收益/代价比。
直白地说：下一步要判断“更激进并行”值不值，不能为了再快一点把资源成本一下子拉太高。

因此，下一阶段目标不是再次证明方向，而是把“已证明有效的结构”收敛成“低资源、可长期保留”的最终工程版本。
