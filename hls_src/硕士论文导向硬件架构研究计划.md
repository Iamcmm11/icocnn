## 1. 计划定位

本文档不是一般性的开发待办清单，而是围绕硕士论文目标制定的研究计划。

核心要求不是“把 HLS 跑通”或“把几个指标压低”，而是要回答下面这个论文层面的关键问题：

`如何针对当前 IcoConv-TempCNN 神经网络的结构特征，设计一套适配该网络的数据流、存储组织与参数化复用硬件架构，并通过可验证的实验说明这种适配为什么有效。`

因此，后续所有代码修改、HLS 优化、资源评估和实验设计，都必须服务于这个主问题。

---

## 2. 论文核心命题

建议将论文主命题收敛为：

`面向 icosahedral ConvIco-TempCNN 的 FPGA 硬件架构适配方法研究`

该命题包含四个必须同时成立的关键词：

1. 面向特定网络，而不是泛化空洞的卷积加速。
2. 强调硬件架构适配，而不是单纯工程实现。
3. 需要体现参数化、可复用、可扩展的结构设计思想。
4. 需要有数学或计算模型上的解释，而不仅是经验调参。

---

## 3. 当前可确立的总体架构思想

结合当前代码和验证结果，已经可以形成一条较清晰的论文主线：

1. `layer0` 作为前端特化层处理。
原因：
`layer0` 的输入通道和旋转维规模小，但输入几何结构特殊，极点处理与 padding 行为更强，适合作为“网络入口特化映射”。

2. `layer1` 作为过渡层处理。
原因：
`layer1` 已经进入主干通道规模，但仍保留从特化输入到统一主干的过渡性质，适合用于验证共享架构是否可平滑引入。

3. `layer2-5` 作为共享参数化主干块处理。
原因：
`layer2-5` 的空间分辨率、通道规模、旋转维和卷积形态高度一致，最适合承载“统一参数化卷积核复用”这一论文核心设计。

这三层思想不能只停留在实现层面，而应上升为论文中的“分层异构映射策略”。

---

## 4. 论文必须回答的四个核心问题

后续工作必须始终围绕下面四个问题展开。

### 4.1 为什么不同层不能采用完全相同的硬件映射方式

需要论证：

1. `layer0`、`layer1`、`layer2-5` 的计算规模和访存模式不同。
2. 它们对极点处理、padding、权重展开和输出后处理的敏感性不同。
3. 因此应采用分层异构映射，而不是强行一套结构包打天下。

### 4.2 为什么 `layer2-5` 适合作为共享参数化块

需要论证：

1. 形状一致性高。
2. 卷积模式重复。
3. 权重和索引结构统一。
4. 共享块设计能够显著减少重复实现成本，并提高论文中的结构表达清晰度。

### 4.3 当前 latency 为什么高

不能只说“报告里数值大”，而要解释其来源。

当前已知的主要来源包括：

1. 主 MAC 大循环中的串行累加依赖。
2. `PadIco` 阶段对输入数组的读端口冲突。
3. 输出顶点后处理阶段对输出数组的读写冲突。
4. 顶层整体尚未形成真正的流式重叠执行结构。

### 4.4 哪些优化是真正“适配网络”的，而不是通用 HLS 套路

后续每一个优化动作都要明确说明：

1. 它针对网络的哪种结构特征。
2. 它改变的是哪一类硬件瓶颈。
3. 它为什么适合当前网络，而不是无差别套模板。

## 5. 需要建立的数学与计算模型

为了让论文具有“算法和架构协同设计”的深度，必须建立最基本的计算模型。

### 5.1 卷积计算量模型

对 ConvIco 的核心计算量，可先采用如下统一表达：

`MACs = T * Cout * Rout * Charts * H * W * Cin * Rin * 7`

其中：

1. `T` 表示时间步数。
2. `Cout`、`Cin` 表示输出和输入通道数。
3. `Rout`、`Rin` 表示旋转维规模。
4. `Charts * H * W` 表示 icosahedral charts 上的空间位置数。
5. `7` 表示紧凑 7 邻域卷积核。

该模型的作用不是追求绝对严密，而是作为后续分析不同层复杂度差异的统一基础。

### 5.2 存储访问模型

需要进一步估计三类访问：

1. 输入特征图访问量。
2. 权重与索引访问量。
3. 中间缓冲与输出回写访问量。

特别是 `PadIco` 和极点平滑相关逻辑，需要单独建模，因为它们不是普通 2D 卷积中的标准访问模式。

### 5.3 延迟分解模型

后续需要将总 latency 分解为：

1. 主卷积计算延迟。
2. Padding 与重排延迟。
3. 输出顶点后处理延迟。
4. 由端口冲突和循环依赖额外引入的调度延迟。

只有建立这种分解模型，后面论文中才能解释“为什么某种优化降低了 latency”。

## 6. HLS 指标的论文解释框架

后续文档和论文中，需要统一对几个 HLS 指标的解释口径。

### 6.1 Estimated Clock

`Estimated Clock` 表示 HLS 对关键路径时钟周期的估计。

它回答的问题是：

`单拍能跑多快`

它不直接回答：

`整个推理一次要多久`

因此，`Estimated Clock` 更适合作为时序约束是否满足的指标，而不是吞吐率指标。

### 6.2 Latency

`Latency` 表示顶层函数一次完整调用的总周期数。

它回答的问题是：

`一次完整计算要跑多少拍`

当 `Latency` 很高时，意味着：

1. 整体响应时间长。
2. 结构中的串行部分过多。
3. 数据流没有形成高效重叠。
4. 存储访问或依赖约束正在限制吞吐。

### 6.3 II

`II` 是 initiation interval，表示流水线中相邻迭代之间至少要隔多少拍才能继续发起。

当关键循环 `II` 很大时，往往意味着：

1. 存储端口不足。
2. 累加依赖严重。
3. 数组布局不适合并行访问。
4. 局部 buffer 组织不合理。

因此，降低 `Latency` 的关键，不是简单把时钟再压低，而是把关键循环 `II` 降下来。

## 8. 下一阶段严格研究路线

### 阶段 A：建立论文级分析框架

目标：
将当前代码与实验结果上升为论文可用的结构化分析。

必须完成的内容：

1. 为 `layer0`、`layer1`、`layer2-5` 分别建立计算量与访存特征表。
2. 总结三种层类型为什么采用不同映射策略。
3. 将当前 HLS 报告中的主要瓶颈整理成“问题来源表”。

产出形式：

1. 分层特征表。
2. 硬件瓶颈分析表。
3. 论文框架中的“问题定义”章节初稿。

### 阶段 B：围绕 latency 来源做结构化优化

目标：
不是盲目优化，而是逐项针对已识别瓶颈做架构改造。

优先顺序：

1. 主 MAC 累加相关优化。
2. 输出顶点后处理读写冲突优化。
3. `PadIco` 输入访问端口优化。
4. 权重/索引访问局部化与 tile 化。

每次优化都必须记录：

1. 改动前后 `Estimated Clock`。
2. 改动前后总 `Latency`。
3. 关键循环 `Final II`。
4. BRAM、DSP、LUT、FF 变化。
5. Python/C 验证是否仍通过。

### 阶段 C：形成“网络适配型硬件架构”表述

目标：
把优化结果上升为可写论文的架构方法，而不是零散 patch。

必须总结出：

1. 前端特化层的映射原则。
2. 过渡层的映射原则。
3. 共享主干层的参数化复用原则。
4. 对应的数据流、buffer 和并行化策略。

### 阶段 D：形成论文实验设计

实验不能只给最终最好结果，必须有分解实验。

建议固定为四组：

1. Baseline：功能正确版本。
2. Baseline + 主 MAC 优化。
3. Baseline + 存储访问优化。
4. Baseline + 参数化共享架构完整版本。

每组对比：

1. 时序指标。
2. latency 指标。
3. 资源指标。
4. 正确性指标。

## 9. 论文中可主张的潜在创新点

结合当前工作，潜在创新点应尽量聚焦，不要发散。

建议收敛成以下三条：

1. 提出一种面向球面 `ConvIco-TempCNN` 的分层异构硬件映射策略。

2. 提出一种针对 `layer2-5` 重复主干结构的共享参数化卷积核架构，以统一处理固定 `Cin=Cout=32`、`Rin=Rout=6`、`H=2`、`W=4` 的卷积块。

3. 针对 `PadIco`、极点平滑和 7 邻域紧凑权重展开等网络特有结构，设计与之匹配的数据流和存储组织方法，并通过 HLS 指标与正确性验证说明其有效性。

这三条创新点都必须建立在“网络适配”而不是“通用加速”上。

## 10. 每一步工作的判定标准

为了防止后续工作偏离论文主线，需要统一判定标准。

### 10.1 可接受的优化

如果某项修改：

1. 能明确对应某类网络结构特征。
2. 能解释它降低了哪类 latency 来源。
3. 能保持正确性验证通过。
4. 资源代价在可接受范围内。

则该优化是有论文价值的。

### 10.2 不建议继续投入的方向

如果某项修改：

1. 只能带来很小的数字改善。
2. 无法解释为什么适合当前网络。
3. 难以上升为方法论。
4. 只是一般性的 pragma 调参。

则该方向不应成为论文主线，只能作为辅助工程细节。

只有这两步明确之后，后续每一次优化才真正是在为论文服务。
