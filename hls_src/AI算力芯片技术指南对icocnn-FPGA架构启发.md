# 《AI 算力芯片技术指南》对 icocnn FPGA 架构的可借鉴要点

## 1. 文档目的

本文档用于整理《AI 算力芯片技术指南：CPU vs GPU vs TPU vs NPU vs LPU》中，**对当前 `icocnn` FPGA 加速主线最有参考价值**的设计思想，并将其转化为后续可执行的架构方向。

本文不追求复述原文，而是回答四个更实际的问题：

1. 哪些观点可以直接借鉴到当前 `IcoConv-TempCNN` 项目。
2. 哪些观点需要改写后才能适配球面卷积与 `ConvIco` 数据流。
3. 哪些观点虽然先进，但当前阶段不适合直接照搬。
4. 下一轮工作最值得优先尝试什么。

---

## 2. 最值得借鉴的总体结论

结合当前项目状态，最值得吸收的不是某一种芯片名字，而是以下三条通用设计思想。

### 2.1 不要追求单一大计算阵列，而要做多个小型、可调度的计算模块

原文中“多个小阵列优于单一大阵列”的判断，对当前项目有很强启发意义。

但在 `icocnn` 中，这个思想不应被简单理解为“直接做一个 `16x16` 的矩阵脉动阵列”，而应理解为：

1. 不要把所有通道、旋转维、空间位置都压进一个统一的大计算体。
2. 应把主干计算组织为多个小型 `ConvIco` 计算模块或计算岛。
3. 每个模块只负责局部 `OC_TILE`、`RO_TILE` 或局部空间 tile。
4. 通过显式调度器统一驱动这些小模块协同工作。

这与当前 `layer2-5` 已经形成的 `co_base + OC_TILE + ri_partial` 路线是相容的，说明已有工作可以继续向“多小型计算岛”演进，而不是推倒重来。

### 2.2 内存墙仍然是 FPGA 加速的第一矛盾

原文强调所有高能效 AI 芯片都在做：

1. 减少片外访存。
2. 增大片上 SRAM。
3. 让数据尽量单向流动、少回头。

这与当前项目高度一致。对 `icocnn` 来说，真正限制性能的核心并不是“DSP 不够多”，而是：

1. `PadIco` 阶段的不规则输入访问。
2. `output_tile` 与 partial sum 的局部归并依赖。
3. 输出后处理与写回阶段尚未完全流式重叠。

因此，后续优化仍应优先围绕：

1. 输入 staging。
2. bank 化片上缓冲。
3. tile 级局部部分和。
4. 阶段化输出收尾。
5. 真正的顶层 `dataflow` 重叠。

### 2.3 价值不在“通用大算子”，而在“编译期可确定的数据流与调度”

原文中 LPU/NPU 的一个关键思想是：通过编译期规划数据流，减少运行时不确定性和调度开销。

对当前项目而言，这一点非常重要，因为你的目标不是做通用矩阵乘平台，而是做：

`面向 IcoConv-TempCNN 的网络适配型 FPGA 架构`

因此，后续最值得坚持的是：

1. 让 `layer0 / layer1 / layer2-5` 继续保持分层异构映射。
2. 让 `layer2-5` 的主路径保持固定的阶段化执行骨架。
3. 把 `frame / tile / ro / ci / ri` 从普通循环变量，上升为架构级调度对象。

## 3. 对当前项目最能直接落地的参考点

以下内容是最值得在 `icocnn` 中继续吸收并落地的方向。

### 3.1 多小型 ConvIco 计算岛，而不是单大计算体

这是当前最有希望进一步形成论文创新点的方向。

建议理解为：

1. 当前已经验证有效的 `OC_TILE`、局部 `kernel_tile`、`ri_partial`，本质上已经是“小型计算模块化”的雏形。
2. 下一步可继续探索把共享计算核拆成多个更明确的 `ConvIco compute island`。
3. 每个计算岛专注处理一个较小的输出通道分块与局部部分和。
4. 多个计算岛由统一的 tile 调度器驱动，而不是通过一个巨大的单体循环完成所有任务。

这条路线的优势是：

1. 与当前代码骨架兼容。
2. 更容易解释为什么小规模结构更适合球面卷积。
3. 比“直接做 TPU 式大脉动阵列”更符合 `ConvIco` 的 7 邻域、小空间、不规则输入特征。

### 3.2 建立“PadIco -> Conv -> PostProcess”全片上阶段化数据流

当前项目已经证明：

1. `staged_input` 对输入供给组织有效。
2. `PadIco` 不应继续直接从顶层大数组取数。
3. `output_post` 作为输出收尾边界是合理的。

因此，下一步非常值得继续推进的，是把这些局部改动上升为更明确的片上数据流链路：

`stage_input -> pad/reorder -> local input tile -> shared ConvIco core -> local psum -> post_process -> writeback`

真正的目标不是某个 pragma，而是：

1. 中间结果尽量不回顶层大数组。
2. 每个阶段都有明确的片上缓冲边界。
3. 为后续双缓冲和 `dataflow` 提前留出结构接口。

### 3.3 继续坚持“片上存储优先”的设计原则

借鉴 NPU/LPU 的思路，后续所有架构尝试都应优先问三个问题：

1. 是否减少了对顶层大数组的反复直接访问。
2. 是否把不规则访问转化成了局部规则访问。
3. 是否把多次读改写变成了局部一次性归并。

对 `icocnn` 而言，更具体地说就是：

1. 输入侧优先做更细粒度 staging 和 bank 复用。
2. 权重与 `kernel_expansion_idx` 优先局部化，不在最深 MAC 路径重复展开。
3. `ri_partial` 与 `output_tile` 的关系优先做“分阶段归并”，不回退到单 bank 原位滚动累加。

### 3.4 把“调度器”做成轻量但确定的结构控制层

不建议当前阶段引入复杂软核 CPU 作为主调度器，但非常建议继续强化“调度层”概念。

可延续当前论文图中的控制层表达：

1. 层选择器。
2. 帧与 tile 调度器。
3. 地址与 bank 控制器。
4. `OC/RO` 分发控制器。

这类控制结构的意义不是“更智能”，而是：

1. 让阶段边界更清晰。
2. 让结构更容易扩展到双缓冲和 `dataflow`。
3. 让论文表达从“代码 patch”上升到“体系结构设计”。

### 3.5 继续走“混合精度服务于架构”的路线

原文中关于低精度推理和能效优势的判断，可以借鉴，但不能简化成“全部 INT8 即可”。

对当前项目，更合理的经验已经很明确：

1. `input_t` 可以相对紧凑。
2. `weight_t` 是当前精度最敏感的控制点。
3. `act_t/acc_t` 需要服务于局部 tile 累加，而不是机械地一味压小。

因此，这条路线后续应继续表述为：

`混合精度不是独立目标，而是为片上存储预算、局部部分和组织和最终性能服务。`

## 4. 可以转化为论文创新点的方向

以下内容最适合进一步凝练成“本文创新点”，而不仅是工程优化项。

### 4.1 多小型计算岛的球面卷积专用架构

可凝练为：

`针对 icosahedral ConvIco 小核、旋转维存在且输入重排不规则的特点，提出多小型 ConvIco 计算岛架构，而非采用单一大规模规则矩阵阵列。`

创新价值在于：

1. 它不是泛化卷积 IP，而是针对球面卷积的网络适配结构。
2. 它能解释为什么当前项目更适合小规模模块化并行。
3. 它和现有 `OC_TILE`、局部 `ri_partial` 结构天然衔接。

### 4.2 面向几何重排的输入准备与局部存储协同

可凝练为：

`针对 PadIco 与球面重排导致的不规则输入访问，提出输入 staging、重排映射与填充帧局部缓存协同的数据准备结构。`

创新价值在于：

1. 这是当前项目特有的瓶颈。
2. 传统 2D CNN 或标准 GEMM 加速器很少需要处理这一层不规则几何重排。
3. 该方向容易和 HLS 报告中的历史端口冲突证据形成因果链。

### 4.3 局部部分和与输出收尾的阶段化组织

可凝练为：

`针对局部输出累加和极点后处理耦合带来的调度受限问题，提出局部部分和分阶段归并与输出收尾解耦架构。`

创新价值在于：

1. 它不是单纯降低 `II`，而是改变了依赖结构。
2. 它已经在当前项目中证明有效。
3. 它能够与“从顶层输出回改迁移到局部 tile 内处理”的工作形成完整故事线。

### 4.4 分层异构映射 + 编译期确定调度

可凝练为：

`针对网络不同层级在几何复杂度、通道规模与访存模式上的差异，采用分层异构映射，并在共享主干块中构建编译期确定的 tile 化执行骨架。`

这能把论文的立意从“优化一个 HLS 工程”抬升为：

`为特定球面神经网络设计网络适配型 FPGA 架构。`

## 5. 当前不建议直接照搬的内容

以下方向虽然来自先进芯片实践，但当前阶段不建议直接搬到项目主线。

### 5.1 不建议直接做通用 GEMM/大脉动阵列主架构

原因：

1. `ConvIco` 不是规则大矩阵乘主导。
2. `PadIco`、重排映射、极点处理和 7 邻域展开会引入额外前后端开销。
3. 直接 im2col/GEMM 化可能把不规则访存问题从计算前端放大，而不是消除。

因此，“大脉动阵列”更适合作为远期探索，不适合当前作为主线。

### 5.2 不建议当前就引入复杂软核指令系统

原因：

1. 当前项目最主要的瓶颈仍是数据流和局部存储组织。
2. 引入软核 CPU 会显著抬高工程复杂度和论文叙述成本。
3. 当前阶段更适合先把静态调度骨架做清楚。

### 5.3 不建议过早推进稀疏计算和动态跳零

原因：

1. 目前没有证据说明这是当前主瓶颈。
2. 稀疏控制逻辑可能打乱现有稳定的数据流骨架。
3. 对当前论文主线而言，收益未必比继续完善片上数据流更直接。

## 6. 对下次工作的具体建议

若把本文作为下一轮工作的参考，建议优先级如下。

### 优先级 A：继续做输入侧与局部缓冲组织

目标：

1. 继续降低 `PadIco` 输入端口冲突。
2. 把输入不规则访问尽量收束到局部缓冲内部。

建议尝试：

1. 更细粒度的输入 tile staging。
2. `ri` 维或局部空间维的 bank 化复用。
3. 为后续双缓冲预留接口。

### 优先级 B：把 `ri_partial` 路线做成更完整的局部部分和架构

目标：

1. 保留当前已验证有效的 partial sum 分段思想。
2. 避免回退到单 bank 原位累加。

建议尝试：

1. 更细粒度的 `ri_partial` bank 化。
2. 两级归并，而不是直接原位写回 `output_tile`。
3. 让局部归并过程更适合后续 `dataflow` 扩展。

### 优先级 C：在稳定阶段边界基础上评估双缓冲与顶层 dataflow

目标：

1. 让 `stage_input / pad / conv / post / writeback` 从串行阶段进一步走向可重叠阶段。

建议尝试：

1. 先只在输入准备与主计算之间做双缓冲。
2. 再评估输出收尾与下一 tile 计算的重叠可行性。
3. 每一步都必须同时记录 `Latency`、关键 `II` 和资源变化。

### 优先级 D：把“多小型计算岛”先做成概念验证版

目标：

1. 不要求一步做到完整阵列化。
2. 先证明“小而分散的计算模块”比“更大的单体结构”更适合当前网络。

建议形式：

1. 先从 `OC_TILE` 的进一步模块化开始。
2. 用论文图和调度图先形成结构表达。
3. 再决定是否值得进入更深的 RTL/HLS 结构实验。

## 7. 可直接用于汇报的简短表述

### 7.1 版本一：工作汇报简版

我们参考了 AI 算力芯片中关于小阵列、片上存储和确定性数据流的设计思想，判断其中最值得借鉴的并不是通用大脉动阵列，而是“多个小型计算模块 + 全片上阶段化数据流”的架构方法。结合当前 `layer2-5` 的实现，我们已经把主路径整理为 `stage_input -> pad_ico_quantized -> init_output_tiles -> main_conv/partial_sum -> post_process -> writeback`，并通过 `staged_input`、`co_base + OC_TILE`、`ri_partial` 和 `output_post` 等局部结构，把原先顶层数组上的直接读改写转成片上阶段化处理。这说明我们后续可以继续沿着网络适配型结构重构推进，而不是转向通用 GEMM 加速器路线。

### 7.2 版本二：偏论文表达版

结合对 CPU/GPU/TPU/NPU/LPU 架构特点的分析，我们认为当前项目最值得吸收的是高能效 AI 芯片在片上存储组织、数据流阶段化和小规模计算模块调度方面的设计思想。针对 `IcoConv-TempCNN` 中存在的球面重排、极点处理和紧凑 7 邻域卷积等特征，当前实现已经从“单点串行累加 + 顶层输出回改”演进到“输入 staging、局部 kernel 装载、`OC_TILE` 分块、`ri_partial` 分段归并、局部 tile 后处理再统一写回”的结构化数据流。后续更适合在这一基础上发展为“多小型 ConvIco 计算岛 + 分阶段片上缓冲 + 编译期确定调度”的专用 FPGA 架构，而不宜直接照搬规则矩阵脉动阵列。

### 7.3 版本三：面向下次工作的汇报版

下一阶段我们计划重点参考 NPU/LPU 式的片上数据流理念，继续解决 `PadIco` 输入端口冲突、局部部分和归并以及输出收尾重叠不足的问题。具体实现上，将以现有 `staged_input -> padded_frame -> kernel_tile -> ri_partial -> output_tile/output_post` 这条片上链路为基础，优先推进三件事：一是把输入侧 staging 做得更细，继续减少 `PadIco` 的不规则直接访存；二是对 `ri_partial` 和 `output_tile` 做更细粒度 bank 化与两级归并，避免回到单 bank 原位累加；三是在阶段边界已经清晰的前提下评估双缓冲和顶层 `dataflow`，并把现有 `OC_TILE` 骨架逐步提升为多小型 `ConvIco` 计算模块的结构表达。

### 7.4 版本四：强调实现真实性的汇报版

我们这次不是停留在“参考了某类芯片思想”的概念层，而是已经把这些思想映射到了当前 `layer2-5` 的具体实现中。输入侧增加了 `staged_input`，使 `PadIco` 不再直接反复访问顶层 `input`；主计算侧引入了 `co_base + OC_TILE` 的显式输出通道分块，并使用 `kernel_tile` 做局部 3x3 展开权重缓存；累加路径不再在最内层直接对 `output` 或单一局部和做反复读改写，而是先写入 `ri_partial`，再归并到 `output_tile`；输出侧则拆成 `post_process_output_tiles()` 和 `writeback_output_tiles()` 两个阶段，并设置 `output_post` 作为收尾边界。

从结果看，这些改动说明我们的方向不是泛泛地“做并行化”，而是在把原先混在一个大函数里的输入重排、局部卷积、部分和归并和输出修正，逐步收束成可调度的结构单元。后续如果继续推进，我们就不是简单加 pragma，而是在现有骨架上继续做输入 bank 化、局部双缓冲和多小型 `ConvIco` 计算模块扩展，这样汇报和论文里都会更有真实性和连续性。

---

## 8. 一句话结论

这篇文章对当前项目最有价值的启发，不是“FPGA 也去做 TPU”，而是：

`把 icocnn 继续做成面向球面卷积的数据流专用架构，用多个小型计算模块、片上阶段化缓冲和确定性调度去解决不规则访存与局部归并瓶颈。`
