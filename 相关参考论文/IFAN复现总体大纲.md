# IFAN 复现与轻量化迭代总体大纲

## 1. 文档定位

本文档用于指导当前 IFAN 工程的后续复现、边缘收束与 FPGA 创新工作。当前项目已经完成了基于 `IcoCNN` 的 IFAN Stage-1/2/3 主线工程搭建，并形成了：

- PHAT + LMS 双特征链路
- IFAN 双分支注意力融合
- LOCATA 单源任务评估
- `IFAN_80 / IFAN_C8_R2 / IFAN_C8_R3` 的统一比较
- `layer0 / layer1 / layer2-5` 的 HLS 与资源分析基础

当前阶段不再以“继续开放式扩很多模型分支”为主，而是以：

`IFAN_80 收束论文复现 + IFAN_C8_R2 收束 IFAN-Edge + FPGA 并列创新`

作为唯一执行框架。

## 2. 当前固定体系

### 2.1 双主线

- `IFAN_80`
  - accuracy-oriented reference
  - 复现主线
  - 论文 gap 解释主线
- `IFAN_C8_R2`
  - edge-oriented reference
  - IFAN-Edge 轻量化主线
  - 默认硬件映射网络候选
- `IFAN_C8_R3`
  - failed ref
  - 只保留为失败参考，不再进入候选主线

### 2.2 当前默认约束

- 本轮默认不新增训练实验，不把 `C=12` 作为默认执行项。
- 当前默认不修改模型代码、不新开模型分支，只同步计划、结论与硬件推进口径。
- 当前 LOCATA 口径固定为本地可运行的 `benchmark2 / eval / task1,3,5 / total=23 recordings`。

## 3. 算法线的最终收束方式

### 3.1 `IFAN_80` 的角色

`IFAN_80` 负责回答：

- 当前 IFAN 是否已经在本地工程里形成正确、完整的论文主线复现
- 与 baseline、与论文最佳结果还差多少
- 哪些差距仍需解释

它不是边缘部署默认网络，而是论文主线与精度参考。

### 3.2 `IFAN_C8_R2` 的角色

`IFAN_C8_R2` 负责回答：

- 在不改前端口径、不改 IFAN 主骨架的前提下，是否存在一个真正可写进毕设的边缘折中点
- 这个折中点是否在 LOCATA 上仍优于 baseline
- 它是否足以作为后续 FPGA 映射的默认网络候选

当前结论已经固定：

- `IFAN_C8_R2` 在统一 LOCATA 四模型对比口径下仍优于 baseline
- 相对 `IFAN_80` 它损失的是平均精度，但换来了约 `75%` 的参数量与 `MAC` 压缩
- 因此它是当前最有意义的 edge point

### 3.3 当前算法创新点的写法

当前算法创新点统一写成两层：

1. 在二十面体输入框架下完成 IFAN 的完整增量复现与 LOCATA 验收闭环。
2. 提出并验证面向 `IcoConv` 主瓶颈的结构化轻量化边缘方案 `IFAN_C8_R2`，在 LOCATA 上仍优于 baseline，同时参数量和 `MAC` 下降约 `75%`。

明确不写：

- “提出新的通道裁剪算法”
- “C8 是新的网络结构理论创新”

## 4. 硬件线的最终收束方式

### 4.1 当前定位

硬件创新点当前固定表述为：

- 面向球面 `ConvIco` 的网络适配型 FPGA 架构
- 重点在数据流、局部缓冲、紧凑 7 邻域权重表示、局部部分和归并、混合精度协同

本轮硬件不追求：

- 完整 IFAN 全链路上板
- 直接模仿 LLM 论文做低成本 PCB 产品化

### 4.2 当前默认网络候选

- `IFAN_80`：精度参考网络
- `IFAN_C8_R2`：边缘实现参考网络

后续整网预算与资源闭合比较，应围绕这两条线展开，而不是继续扩更多模型版本。

### 4.3 当前下一步

本轮硬件的下一步固定为：

1. `layer1` 继续向 `layer2-5` 的结构化骨架靠拢
2. `layer2-5` 继续解决 `PadIco` 输入端口冲突和 `output_tile` 累加调度
3. 基于真实 HLS 报告做整网预算，重点比较 `IFAN_80` 候选与 `IFAN_C8_R2` 候选的资源闭合性

## 5. 从 `Hummingbird+` 借鉴的方法论

参考论文：

- `相关参考论文/Advancing FPGA-based LLM Deployment from Research Prototype to Edge Product.pdf`

当前只迁移方法论，不迁移 LLM 专属结构。

### 5.1 可直接借鉴的部分

- 先做**平台/资源/带宽/容量**建模，再谈加速核
- 优先 **memory-first**，而不是 compute-first
- 倾向“多个小型、可调度的计算模块”，而不是单一大阵列
- 尽量减少通用大 IP 堆叠，强调与网络结构匹配的数据流组织
- 报告原始硬件指标：`LUT / DSP / BRAM / FF / latency / 时钟`

### 5.2 不直接照搬的部分

- token processor
- MoE / KV cache
- LLM 的 decode / prefill 数据流
- 低成本 PCB 产品化路线

### 5.3 对当前项目的实际启发

对当前 `ConvIco` 硬件线，`Hummingbird+` 最值得吸收的不是某个具体结构，而是：

1. 从“研究原型”转向“可闭合的系统方案”思维
2. 先明确容量、访存、资源和控制路径，再谈局部算子加速
3. 把硬件创新写成“网络适配架构”，而不是“某个孤立 HLS pragma 优化”

## 6. 当前执行优先级

当前优先级固定为：

1. 先同步主线文档口径
2. 再以 `IFAN_C8_R2` 为默认网络候选推进硬件
3. 不在本轮开启新的模型分支

对应到文档与工作流：

1. 先同步 `IFAN_IcoConv主干轻量化与C8实验计划.md`
2. 再同步 `IFAN复现.md`
3. 再以本文件作为当前阶段总纲收束
4. 最后把硬件侧整网预算与方法论补成可以写进毕设的架构章节
