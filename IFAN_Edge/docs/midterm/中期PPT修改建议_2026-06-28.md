# 中期 PPT 修改建议

> 基于 `IFAN_Edge/docs/midterm/中期.pdf` 当前版本、你导师的口头反馈，以及我们现在论文主线的统一逻辑整理。  
> 目标不是“把每页内容再写多一点”，而是把整套 PPT 改成一条更像硕士中期答辩的故事线：**问题定义清楚、创新点收束明确、结果与硬件口径可信**。

## 1. 先说总判断

你现在这套 PPT 的核心问题，不是“没做内容”，而是“**主线出现太晚**”。

当前版本从第 3 页到第 8 页，连续出现了：

- 背景
- 研究现状
- 研究目标
- 研究挑战
- 实验环境
- baseline 分析

这些内容单看都对，但因为**整体总览没有尽早出现**，评委会感觉你一直在铺垫，却不知道你到底“这篇课题要解决什么、已经做成了什么、创新点是什么”。

所以这次修改的核心方向是：

1. **总览提前。**
2. **把算法部分收束成一个创新点，而不是拆成很多平级小改动。**
3. **把硬件部分收束成第二个创新点，并用“可综合的资源/时延/吞吐证据”证明真实性。**

## 2. 当前版本里最该先修的显性问题

这些问题不属于学术逻辑，但会非常影响专业感，建议你在改结构前先处理：

1. 从第 6 页开始，多页底部都出现了一大段重复的叠加文字。
   这看起来像是母版残留文本框或被复制到多页的隐藏说明文字。这个问题必须先删掉，不然整套 PPT 会显得非常乱。

2. 命名不统一。
   现在同时出现了 `Mamba / Maba / Mabma`，还有 `IcoConv / llcoConv`、`Enhnancement` 这类拼写问题。答辩里一定要统一。

3. 硬件资源页用的 HLS 数字不是最新口径。
   你当前 PDF 里的资源页看起来还是旧数据，建议全部换成当前本地最新 summary。

4. 多页标题偏“阶段标签”而不是“功能标签”。
   比如 `Stage2/Stage3`、`轻量化设计实验验证`、`Maba时序增强结果`，看起来更像实验周报，不像中期答辩。

## 3. 对导师 7 个问题的逐条建议

### 问题 1：第三页选题背景相关性不强，阵列演进和算法转型像在“随便说说”

这个判断是对的。

你现在第 3 页的两句：

- “从传统规则阵列向分布式阵列发展”
- “从人工特征向深度学习模型转型”

都不算错，但和你当前课题的直接关系不够强。你的课题并不是：

- 做分布式阵列设计；
- 做阵列形态综述；
- 也不是做“传统算法到深度学习”的历史回顾。

你的背景应该直接服务于你这篇课题的主问题，所以建议改成：

**新的背景页标题：**

`研究背景：纯声源方位估计的边缘部署需求`

**这一页只讲三件事：**

1. 纯声源方位估计在机器人听觉、会议终端、人机交互里仍然是独立而核心的感知任务。
2. 复杂声学环境下，定位稳定性仍然是难点。
3. 端侧部署要求我们不仅看精度，还必须看参数量、MAC、缓存和时延。

**这三件事的小标题可以直接起成：**

- `核心应用场景`
- `复杂环境挑战`
- `端侧部署约束`

如果你想更学术一点，也可以写成：

- `任务应用价值`
- `真实环境下的定位难点`
- `边缘实现约束`

我更推荐第一组，因为更短、更适合 PPT。

**第三页建议改法：**

可以保留你现在第三页里“SSL 应用场景”的那部分视觉元素，但不要再保留“阵列演进”和“算法转型”这两句大字。

更准确的改法是：

1. 左侧或上方保留场景示意：
   机器人听觉、会议终端、人机交互这类应用场景可以继续留着，因为它们确实能说明课题价值。
2. 右侧或下方改成三块短内容：
   - `核心应用场景`：纯声源方位估计仍是空间感知系统中的基础能力。
   - `复杂环境挑战`：低 SNR、强混响、声源/麦克风运动会导致空间响应不稳定。
   - `端侧部署约束`：不仅要看定位精度，还要控制参数量、MAC、缓存和时延。

**所以你的理解“保留第三页的场景部分，再把第六页的复杂声学挑战和边缘部署核心约束拿过来”总体方向是对的。**

但有一个关键点：

- **不要直接粘原文。**
- 要把第六页那两块内容压缩成第三页的两个短框，每块 1 句话到 2 句话。

因为第六页现在的问题本来就是字多、信息挤，如果你直接搬到第三页，第三页会继续显得像“说明书”，而不是背景页。

**一个可直接放进第三页的文字版本是：**

`核心应用场景`
纯声源方位估计仍是机器人听觉、会议终端和人机交互中的基础感知任务。

`复杂环境挑战`
低信噪比、强混响以及声源/麦克风运动会导致空间响应扩散、伪峰增强和跨帧波动。

`端侧部署约束`
边缘设备不仅要求定位有效，还要求模型在参数量、MAC、缓存和响应时延上可落地。

**结论：**

第三页不要再讲“阵列演进史”。  
如果你很想保留“传统到深度学习”的技术演变，它最多只适合压成第四页研究现状中的一条背景线，而不是单独撑满一页。

### 问题 2：第四页还行，但第五页衔接不好；总览要不要提前；五六七页逻辑不对；“纯 DOA 估计”这个小标题不够专业

这里我给你一个明确判断：

**总览必须提前，但研究现状页也不能完全删。**

不要等到第 8 页才让评委看到“你到底做了哪几件事”。  
正确顺序应该是：

1. 背景
2. **研究现状与研究空白**
3. **课题总览**
4. baseline 为什么选它
5. 算法主线
6. 硬件主线

所以：

- 第 4 页不建议继续做“技术演进脉络”大综述，而建议改成一页非常克制的**研究现状与研究空白**。
- 第 5 页改成真正的**课题总览页**。
- 第 5 页不要继续叫“端侧部署的适配性”或“研究意义”。
- 研究意义应该在第 3 页背景末尾讲完，而不是拖到第 5 页。

**你现在第 5/6/7 页的问题，不是内容错，而是三页都在讲“为什么做”，没有尽快进入“我做了什么”。**

我建议重排成：

1. 第 3 页：`研究背景：纯声源方位估计的边缘部署需求`
2. 第 4 页：`研究现状与研究空白`
3. 第 5 页：`课题总览：两条主线与两个创新点`
4. 第 6 页：`为什么选择 icoCNN baseline：优势、瓶颈、切入点`
5. 第 7 页：`创新点 1：面向边缘部署的 DFA-IcoNet-Edge 算法主线`
6. 第 8 页：`创新点 1 的结果收束：IFAN_80、IFAN_C8_R2、Mamba 的角色`

关于“纯 DOA 估计”这个小标题：

- 不要直接写“纯 DOA 估计”。
- 第一次出现可以写成：`声源方位估计（DOA）主线`
- 后面统一写“声源方位估计”或“方位估计主线”。

这样对非本领域老师更友好，也更正式。

### 研究现状页应该怎么放

如果第三页已经改成你现在这版“背景：应用场景 + 复杂环境挑战 + 边缘部署约束”，那**下一页最合适的衔接就是研究现状与研究空白**。

原因很简单：

- 第三页回答的是：**为什么这个问题值得研究**
- 第四页应该回答：**别人现在主要做到哪了，但和我的问题并不完全重合**
- 第五页再回答：**所以我这篇课题具体怎么切进去**

也就是说，研究现状页不是可有可无，但它不应该再写成“完整领域发展史”，而应该写成：

`研究现状与研究空白`

### 这页顶部标题和小字说明怎么写

如果你这一页准备放在第三页背景之后、第五页总览之前，我最推荐的写法是：

这版的优点是：

### 研究现状页怎么写才不和你的方向打架

你现在的真实情况不是“这个方向没人做，所以我没法讲研究现状”，而是：

- 大家主要在做更大的任务，比如多声源、SELD、复杂语义联合建模；
- 也有人在做 FPGA/CNN 加速，但大多是通用网络或通用加速框架；
- **而“纯声源方位估计 + 边缘部署 + 二十面体网络适配”这三个点的交叉区域相对不足。**

这恰恰就是你课题有意义的地方。

所以第四页不要说：

- “边缘部署几乎没人做”
- “这个方向没人研究”

这种说法太绝对，老师很容易继续追问。

更稳的表达应该是：

`现有研究更多聚焦定位精度提升和任务扩展，而面向纯声源方位估计的边缘部署研究，尤其针对二十面体网络结构的算法—硬件协同优化，仍相对不足。`

### 研究现状页建议结构

这页建议只保留 3 个框，加 1 个“研究空白”总结框。

**左侧三块：**

1. `研究方向一：定位任务持续扩展`
   从单源 DOA 走向多源定位、SELD 与距离估计，任务更丰富，但模型更复杂。

2. `研究方向二：学习模型精度持续提升`
   从 CNN 到 CRNN、Transformer，复杂场景精度更强，但参数量和 MAC 也同步上升。

3. `研究方向三：硬件加速研究多为通用框架`
   现有 FPGA/CNN 加速更多针对通用卷积网络，较少直接面向声源方位估计与二十面体卷积结构。

**右侧或下方单独收束：**

`本课题研究空白`
现有工作在“任务更复杂”或“模型更大”上推进较多，但面向纯声源方位估计的边缘部署问题，特别是二十面体网络从算法结构到硬件映射的协同优化，仍缺少系统性研究。

### 研究现状页可直接引用的论文

下面这 3 组参考文献都可以直接对应你第四页的三个研究方向，而且都优先选了你本地已有、`2020` 年之后的论文。

#### 研究方向一：定位任务持续扩展

这组文献用来支撑“定位任务已经从单一 DOA 走向更复杂的多任务或更灵活阵列建模”。

1. Axel Berg, J. Gulin, et al., `wav2pos: Sound Source Localization using Masked Autoencoders`, ICASSP 2024.  
   适合原因：它体现了声源定位研究正在朝更灵活的表示学习和更复杂阵列适配方向发展，不再局限于固定阵列、固定任务。  
   你本地已有：`相关参考论文/wav2pos` 对应条目已在文献阅读中整理。

2. J. Wei et al., `Real-Time Sound Event Localization and Detection: Deployment Challenges on Edge Devices`, arXiv 2024.  
   适合原因：这篇虽然更偏 SELD/部署挑战，但正好能证明“现在很多工作已经把定位问题扩展到更复杂的联合任务”，从而反衬你为什么要回到更聚焦的方位估计主线。

#### 研究方向二：学习模型精度持续提升

这组文献用来支撑“模型从 CNN 走向更强的结构，复杂场景精度更强，但复杂度也上来了”。

1. D. Diaz-Guerra, A. Miguel and J. R. Beltran, `Direction of Arrival Estimation of Sound Sources Using Icosahedral CNNs`, IEEE/ACM TASLP, 2023.  
   适合原因：这是你 baseline `icoCNN` 的直接来源，非常适合说明“球面几何建模 + CNN”这条线已经证明有效。

2. X.-C. Zhu et al., `IFAN: An Icosahedral Feature Attention Network for Sound Source Localization`, IEEE TIM, 2024.  
   适合原因：它正好对应你现在的算法主线来源，能说明研究已经从基础球面 CNN 进一步发展到双特征、注意力融合这类更强模型。

#### 研究方向三：硬件加速研究多为通用框架

这组文献用来支撑“硬件和边缘部署方向确实在发展，但大多数还是面向通用神经网络框架，而不是直接针对二十面体 SSL 结构”。

1. `SAF-CNN: A Sparse Acceleration Framework of Convolutional Neural Network for Embedded FPGAs`, 2023.  
   适合原因：它很典型，代表“面向嵌入式 FPGA 的通用 CNN 稀疏化加速框架”，正好能用来说明现有硬件研究更多是通用框架。

2. B. Ramhorst, V. Lončar and G. A. Constantinides, `FPGA Resource-aware Structured Pruning for Real-Time Neural Networks`, ICFPT 2023.  
   适合原因：这篇强调的是资源感知剪枝和通用实时神经网络部署，也更偏“通用优化框架”，非常适合和你这种面向 IcoConv 特殊结构的课题形成对照。

### 问题 3：第八页 research analysis 怎么讲；想先讲 baseline 和问题，再用箭头对应总览；总览放到这里是不是太靠后

是的，**总览放到第 8 页已经太靠后了**。

第 8 页更适合承担的功能，不是“第一次出现总览”，而是：

`baseline 的优势、瓶颈、对应改法`

也就是说，这一页最适合做成一张**问题—方案映射页**。

建议保留你现在这页的主体思路，但改成更清晰的三段结构：

1. 上半部分：为什么选 `icoCNN baseline`
2. 中间部分：baseline 四类瓶颈
3. 下半部分：用箭头把每个瓶颈映射到你的对应工作

建议做三条显式箭头：

- `单一 PHAT 特征不稳` -> `PHAT + LMS 双特征`

### 问题 7：硬件部分作为第二个创新点，现在只有资源映射表；能不能直接算某个 IP 在选定时钟下的效率，和 GPU 比；怎么展示真实性

这里分成两个问题看。

**第一，能不能算？**

可以算，但你现在更适合算的是：

- **单 IP 的理论执行时间**
- **单 IP 的理论吞吐**

而不是直接写“比 GPU 快多少倍”。

因为如果要和 GPU 做 speedup 对比，至少要统一：

- 同一个 workload
- 同一个精度口径
- 同一个 batch / 输入尺寸
- 是否计入 host-device / PS-PL 数据搬运

这些条件你现在都没有严格对齐，所以**不建议在中期主 PPT 里直接写“比 GPU 提升 X 倍”**。

**第二，怎么讲真实性？**

我建议你用“三层证据”来讲：

1. `HLS 可综合`：有 BRAM / DSP / LUT / FF / Latency / Clock
2. `吞吐可估算`：用 `MAC / (Latency × Clock)` 算单 IP 吞吐
3. `边界明确`：强调这是单层级 IP，不含整网调度和传输开销

### 一个你现在就能用的硬件口径

基于你本地最新 `layer2-5` summary：

- `Estimated Clock = 4.209 ns`
- `Best Latency = 1,956,787 cycles`
- `MAC = 536,739,840`

可以直接得到：

1. 按目标 `5ns` 时钟估算：
   - 单次执行时间约 `9.78 ms`
   - 吞吐约 `54.9 GMAC/s`
   - 若按 `1 MAC = 2 ops` 计，则约 `109.7 GOPS`

2. 按当前估计时钟 `4.209ns` 估算：
   - 单次执行时间约 `8.24 ms`
   - 吞吐约 `65.2 GMAC/s`
   - 若按 `1 MAC = 2 ops` 计，则约 `130.3 GOPS`

**建议你在 PPT 里这样写：**

`以 layer2-5 单 IP 为例，当前 HLS 综合结果下，目标 5ns 时钟对应单次执行时间约 9.78ms，对应理论吞吐约 54.9 GMAC/s（约 109.7 GOPS）。该结果仅反映单层级 IP 的计算能力，不含 PS/PL 通信与整网调度开销。`

这句话的好处是：

- 有数字；
- 有公式依据；
- 又不会夸大成“整网已经超过 GPU”。

### 相关论文里一般怎么比

我又对你本地那三篇新增硕士论文做了一次针对性筛查，结论很明确：

- **很少有人直接拿“时钟频率”去和 GPU 对比。**
- 更常见的对比是：
  - `CPU / GPU / FPGA` 的**推理时间**
  - `FPS`
  - `GOPS / GMAC/s`
  - `功耗`
  - `能效`，比如 `GOPS/W` 或 `FPS/W`
  - 有时还会补 `FPS/DSP`、`FPS/BRAM`、`FPS/LUT` 这类资源归一化指标

本地三篇论文里可以直接看到：

1. **孙煜这篇**  
   直接比较了 `CPU、GPU、FPGA` 的推理时间。  
   文中给的是：`CPU 12.74s，GPU 6.31s，FPGA 2.16s`。  
   这说明如果任务完全一致、输入完全一致，那么“推理时间对比”是最直观也最容易讲的。

2. **王枭这篇**  
   更强调 `GOPS` 和 `GOPS/W`。  
   这属于更偏硬件论文的写法：不一定非和 GPU 逐项比，但会把吞吐和能效作为核心指标。

3. **项浩斌这篇**  
   用了 `FPS`、`GOPS`、`FPS/W`、`FPS/DSP`、`FPS/BRAM`、`FPS/LUT`。  
   这类写法很适合“说明硬件设计是不是划算”，尤其适合 FPGA 论文。

### 所以你中期答辩最稳的比较方案

你现在**只有单个 IP**，还没有整网、没有统一 GPU 端复现实验，也没有严格对齐的 host-device 数据传输口径。  
所以最稳妥的方案不是一步到位硬比 GPU，而是分两层讲：

#### 层 1：本页主结论讲单 IP 的真实性

直接讲：

- 当前 `layer2-5` 已完成 HLS 综合；
- 有明确的 `Clock / Latency / BRAM / DSP / LUT / FF`；

- 这能证明该 IP 不是停留在概念图，而是已经进入可量化分析阶段。

#### 层 2：补一个“参考性 GPU 对比口径”

你可以讲：

`由于当前仅完成单 IP 级别的 HLS 验证，尚未完成整网级 GPU/FPGA 严格同口径对比，因此本阶段不直接报告整网 speedup，而是先给出单 IP 的理论吞吐，并在后续整网集成后补充与 GPU 推理时间的统一比较。`

这个说法非常稳。

### 如果你坚持想在中期里“尽量和 GPU 沾一下”

我建议你只说**对比思路**，不要说“我们已经超过 GPU”。

你可以写成：

`参考已有 FPGA 部署论文，后续整网对比将采用统一输入规模下的 CPU/GPU/FPGA 推理时间、吞吐（GOPS）和能效（GOPS/W）三类指标。当前阶段先验证单 IP 的 HLS 可综合性与理论吞吐。`
