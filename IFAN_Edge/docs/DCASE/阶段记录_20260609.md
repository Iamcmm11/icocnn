# DCASE Stereo Folded-Azimuth 阶段记录

## 当前目标

在不影响冻结主线 `ifan_c8_r2_maba_pre_readout_best` 的前提下，新建一条独立的 DCASE stereo 训练/评估分支。第一版保持 IFAN 主干不变，只替换：

- 输入口径：从 `benchmark2` 12 通道阵列改成 2 通道 stereo 代理前端
- 训练目标：从 LOCATA 风格 3D DOA 回归改成水平面 `folded-azimuth` 单位向量回归
- 主指标：统一使用 `DOA error (deg)`

## 已完成内容

### 1. 独立训练分支骨架

已新增以下文件：

- `IFAN_Edge/configs/dcase_stereo_folded_azimuth_c8_r2_maba_pre_readout.toml`
- `IFAN_Edge/scripts/train_dcase_stereo_ifan.py`
- `IFAN_Edge/ifan_edge/training/dcase_stereo.py`

其中：

  `IFAN_Edge/outputs/stage3/ifan_stage3_long80_c8_r2_maba_pre_readout_20260518_215408/checkpoints/best_rmsae.pt`
- 不复用冻结 run 的 resume 逻辑，不写入原输出目录

### 2. DCASE 数据与目标构造

训练分支已支持：

- 从 `datasets/DCASE2025_Task3/locata_like_strict/manifest_all.csv` 读取 train/validation 母集
- 只保留 `dev-train-sony` 与 `dev-train-tau`
- 固定随机种子 `42` 做分层切分
- 从 `datasets/DCASE2025_Task3/locata_like_devtest_strict/manifest_all.csv` 读取最终测试集
- 音频重采样 `24 kHz -> 16 kHz`
- 窗长/步长：`K=4096`，`step=3072`
- 2 通道 stereo 代理阵列：`[[-0.04, 0, 0], [0.04, 0, 0]]`
- 目标改成水平面 `folded-azimuth` 对应的 3D 单位向量

### 3. 训练损失与验证指标

当前训练分支：

- 保留 IFAN 主干和 3D 输出头
- 损失为预测 3D 坐标与“水平面 folded-azimuth 目标向量”的 MSE
- 仅在 metadata 标记 active 的窗口上计算损失
- 额外排除最前面的 `5` 个窗口

验证与测试阶段：

- 主指标：`DOA error (deg)`
- 辅助指标：`Folded Az RMSE`、`Horizontal Assumption RMSAE`

### 4. 评估链路统一

`IFAN_Edge/scripts/evaluate_stage3_dcase2025.py` 已改成复用 `ifan_edge.dcase_stereo` 中的共用逻辑，训练和评估共享：

- metadata 解析
- stereo 代理前端
- folded-azimuth 映射
- `DOA error (deg)` 统计口径

## 当前判断

- 训练链和评估链已经形成闭环
- 新分支不会影响冻结主线
- 10 轮结果已经证明“输入/输出口径对齐”是有效方向
- 现阶段最合理的下一步仍然是先继续沿当前方案加轮次，而不是立刻改成全新的 azimuth-only 输出头

## 下一步建议

### 1. 先继续当前方案，而不是马上换头

原因：

- 当前 10 轮已经显著优于 zero-shot
- validation 曲线仍在下降，只是接近放缓，还不能说明现有头已经到极限
- 如果现在直接切到真正的 azimuth-only 头，会同时改变输出层、损失定义和评估行为，变量太多，不利于判断收益来源

### 2. 建议先把当前方案扩到一个更完整的训练轮次

建议下一步：

- 继续在当前结构下训练到 `20` 或 `30` 轮
- 保持同一套 stereo frontend、同一套 folded-azimuth 目标
- 继续用 `DOA error (deg)` 作为主指标

目标是先确认：

- 现有“水平面目标向量 + 3D 输出头”还能不能继续下降
- 它最终能稳定降到什么区间
- 当前方案是否已经足够支撑中期里的迁移实验结论

### 3. 何时再考虑真正的 azimuth-only 头

只有在下面情况出现时，再考虑进入下一阶段：

- 当前方案在 `20~30` 轮后明显进入平台
- validation / test `DOA error (deg)` 长时间不再改善
- 或者我们发现 3D 输出头带来的表示冗余明显限制 folded-azimuth 收敛

那时再做 azimuth-only 头会更合理，因为：

- 我们已经有一个稳的 stereo baseline
- 也更容易判断“收益来自输出头”还是“收益来自前端/训练口径对齐”

## 阶段结论更新

### Stage 1 结论

第一阶段目标已经完成：

- stereo frontend 对齐是有效的
- folded-azimuth 训练目标对齐是有效的
- 在不改冻结主线结构的前提下，DCASE 跨数据集迁移结果已明显优于 zero-shot

### 下一步判断

不建议再把“继续加大轮次”作为优先方向。

原因：

- 80 轮相对 10 轮仍有收益，但已经进入明显边际递减
- moving 子集没有同步继续变好
- 当前剩余误差更可能来自“输出层参数化方式不自然”，而不是简单训练不够

因此，下一步更合理的方向是：

- 保留当前 stereo frontend
- 保留当前 train / validation / test 切分
- 进入 Stage 2：改成真正的 `azimuth-only / folded-azimuth` 输出头

## 后续工作切换原则

从这一节点开始：

- `继续堆轮次` 不再作为默认优先项
- `Stage 2 azimuth-only 头改造` 作为主线推进方向
- 如果 Stage 2 完成后仍需要再做长轮次训练，再以新输出头为基础重跑训练

## 阶段结论再更新

到目前为止，可以把 DCASE 独立分支分成两步来总结：

- Stage 1：证明 stereo frontend + folded-azimuth 目标对齐有效
- Stage 2：证明把输出层改成真正的 azimuth-only 头后，性能进一步明显提升

因此，DCASE 分支当前推荐的主线应切换为：

- 保留 stereo frontend
- 保留当前 strict 数据切分
- 以 azimuth-only 头作为后续默认结构

不再建议继续围绕 Stage 1 的 3D 输出头加大轮次。
